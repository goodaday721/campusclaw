# 设计：技能上传与关怀式对话

## 一、技能上传

### 接口

`POST /api/skills/import`，`multipart/form-data`，字段 `file`。

| 情况 | 状态码 |
|---|---|
| 缺文件 / 文件名空 | 400 |
| 扩展名不是 `.md` / `.json` | 415 |
| 超过 64KB | 413 |
| 非 UTF-8 | 400 |
| 解析失败（缺名称/正文、JSON 非法） | 400 |
| 工具引用四查不通过 | 400 |
| 本班已存在同名技能 | 409 |
| 学生调用 | 403 |
| 未登录 | 401 |
| 成功 | 201 |

### 两种输入格式

`.md`：直接交给 `skill_source.parse`（`名称/适用条件/工具/资料/启用` + 空行 + 正文）。

`.json`：两种形态
1. `{"source": "<整段 source 文本>"}` → 再走 parse；
2. 扁平 `{"name", "description", "trigger", "tools", "subject"}` → 直接组装。

### 为什么强制停用 + 规整 source

- 导入后 `enabled=0`：教师先看到列表里新增条目，确认内容再启用，避免未知技能包立即影响学生回答。
- `source` 统一用 `_canonical_source` 重写（含 `启用：否`）：编辑框只接受单段 source 文本，若保留原始 JSON，教师点「编辑 → 更新」必然解析失败。

### 与既有校验的关系

工具引用复用 `validate_reference`（格式 → 已登记 → 已连接 → 在清单内），与手工创建完全一致；没有新增校验分支。

## 二、关怀式对话

### 为什么不是无条件注入

若把关怀技能当普通技能注入，每次回答都会带上「先共情」的指令，会稀释解题引导的语气，也让所有对话的 prompt 变长。因此用确定性门控：只有消息命中挫败词表才注入。

### 词表

`不会 / 听不懂 / 看不懂 / 学不会 / 太难 / 好难 / 崩溃 / 焦虑 / 不想学 / 想放弃 / 放弃 / 压力 / 害怕 / 没信心 / 学不下去`

判定函数 `app.services.chat.needs_care(text)`，纯本地、无模型调用。

### 两条零命中文案的取舍

系统有两处「零证据 → 固定文案」短路（`chat.start` 与 `_complete`）。关怀轮次两处都豁免：

- 若仍短路，学生在说「我完全不会，想放弃」时会收到「资料中未找到相关内容」——技术上正确、体验上最糟。
- 豁免后模型在系统提示中拿到关怀技能段落，做共情 + 小步引导；`citations` 仍为空，不伪造引用。

### 可测试性

注入与否体现在：`model_gateway.chat_stream` 收到的 system 消息是否含 `【技能：关怀式对话】`，以及持久化消息的 `skill_name`。两者都被测试覆盖。

## 测试策略

- `tests/test_skill_import.py`（16 例）：md/json 正常、7 类失败、停用→启用、跨班同名独立、审计字段。
- `tests/test_care_skill.py`（7 例）：seed 与绑定、词表判定、命中注入、普通不注入、停用不注入、零命中仍调模型、普通零命中保持固定文案。
